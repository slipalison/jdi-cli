# JDI — State Schema

Flat-file state. No DB. No server. Markdown + YAML frontmatter where needed.

Locked decisions live in `DECISIONS.md`. Audit trail of created specialists/agents lives in `registry.md`. Per-phase learning lives in `SUMMARY.md` and `REVIEW.md` per phase.

## Schema versions

Field `schema_version` in `STATE.md` indicates the phase identification model:

| Version | Phase ID | Folder | Multi-dev safe? |
|---|---|---|---|
| 1 (legacy) | numeric position (`current_phase: 5`) | `.jdi/phases/NN-slug/` | NO — numeric positions collide across branches |
| 2 (current) | canonical slug (`current_phase_slug: auth-flow`) | `.jdi/phases/<slug>/` | YES — slug is unique; slug collision surfaces as a visible git conflict |

v1 projects can migrate via `/jdi-migrate-phases` (non-destructive: does not rename folders, just stamps `schema_version: 2` + `current_phase_slug` in STATE.md — no manifest file is needed or written). Every JDI command accepts slug OR integer position in v2; the resolver helper (`npx -y jdi-cli resolve-phase`, backed by `bin/lib/jdi-resolve-phase.{sh,ps1}`) normalizes.

When `schema_version` is absent, default = 1 (compatibility).

## Phase status is DERIVED from artifacts

There is no per-phase status field to maintain. The lifecycle stage of a phase is derived from which artifacts exist in its folder:

| Artifact present | Derived status |
|---|---|
| `SHIPPED.md` | done |
| `REVIEW.md` | verified |
| `SUMMARY.md` | executed |
| `PLAN.md` | planned |
| `CONTEXT.md` | discussed |
| (nothing) | pending |

Priority order: most advanced artifact wins. `ROADMAP.md` carries no status lines and `STATE.md` is advisory — gates check artifacts, never state fields. This keeps every shared file conflict-free across parallel team branches.

## Full tree

```
.jdi/
+-- PROJECT.md           vision + stack + code-design LOCKED. Immutable after /jdi-new
+-- ROADMAP.md           sequential phase list (slug + goal). NO status lines
+-- STATE.md             advisory next-step hint. UNTRACKED (gitignored) — regenerated when absent
+-- DECISIONS.md         append-only. Mini ADR. D-1, D-2, ... (v1) or D-{date}-{slug}-{seq} (v2)
+-- config.json          token/context budget + thresholds. Editable
+-- specialists.md       per-project routing (generated by /jdi-bootstrap)
+-- reviewers.md         per-project routing
+-- registry.md          audit trail (R-1, R-2, ...) — everything /jdi-create or /jdi-bootstrap created
+-- skills-registry.md   registry of reusable skills (template shipped; used by jdi-architect)
+-- todos.md             scope creep captured by the asker (optional)
+-- agents/              per-project specialists
|   +-- jdi-doer-{slug}.md
|   +-- jdi-reviewer-{slug}.md
+-- phases/
|   +-- setup-api/                  v2 layout: folder = canonical slug
|   |   +-- CONTEXT.md   output of /jdi-discuss (asker)
|   |   +-- PLAN.md      output of /jdi-plan (planner)
|   |   +-- SUMMARY.md   output of /jdi-do (doer)
|   |   +-- REVIEW.md    output of /jdi-verify (reviewer)
|   |   +-- SHIPPED.md   output of /jdi-ship — per-phase done marker
|   |   +-- LOOP.md      audit trail of /jdi-loop (only if ralph mode was used)
|   +-- 02-old-phase/               v1 legacy layout preserved post-migration (NEVER renamed)
|   +-- ...
+-- archive/             old phases moved by /jdi-ship compaction (optional; has index.md)
```

Nothing from `templates-jdi-folder/` is copied into `.jdi/` automatically. Files are generated directly by the commands (defaults are inlined in the command prompts):
- `/jdi-new` creates PROJECT, ROADMAP, STATE, DECISIONS, config.json, .gitattributes, .gitignore entry
- `/jdi-bootstrap` creates specialists.md, reviewers.md, registry.md + agents/*

## Merge safety (team usage)

Three mechanisms keep `.jdi/` conflict-free across parallel branches:

1. **Derived status** — no shared file records phase progress; artifacts in the phase folder do (see above). ROADMAP.md has no status lines; ship never edits it.
2. **STATE.md untracked** — it is a per-clone advisory cache in `.gitignore` (every command rewrites it, so versioning it guaranteed a conflict on every merge). Commands regenerate it from artifacts when absent (fresh clone): current phase = first ROADMAP phase without SHIPPED.md.
3. **`merge=union`** on the append-only files (`DECISIONS.md`, `todos.md`, `registry.md`, `specialists.md`, `reviewers.md`, `skills-registry.md`, `archive/index.md`) AND, since 0.11.0, **`ROADMAP.md`** — `/jdi-issue` made phase appends a per-card operation, so parallel appends must auto-merge. The ROADMAP trade-off (a racing `remove-phase` can resurrect a removed block) is rare, visible in `/jdi-status`, audited by `D-{date}-{slug}-rm`, and fixed by re-running the remove. NOT applied to PROJECT.md or config.json — conflicts there must stay visible. Also since 0.11.0 the ROADMAP stores no `total_phases` counter (derived from heading count — a stored aggregate conflicts on every parallel add and union-merges stale).

Migration for pre-0.3.0 projects: `git rm --cached .jdi/STATE.md && echo '.jdi/STATE.md' >> .gitignore`, and append the union block to `.gitattributes` (or re-run the adopter Step 8 snippet — it is idempotent).

`config.json` is written inline by `/jdi-new` (Write, only if absent). `templates-jdi-folder/config.json` is the canonical reference for the default, shipped by the npm package for manual regeneration. Same idea for `skills-registry.md`: `templates-jdi-folder/skills-registry.md` ships the canonical empty registry.

## PROJECT.md

```markdown
# {project_name}

## Vision
1-3 lines. What the project solves.

## Type
web app | cli | api | lib | mobile

## Stack
- Language: {language + version}
- Framework: {framework + version}
- Key dependencies: {list}

## Code Design
**LOCKED:** {DDD | Vertical Slice | Hexagonal | Clean | Onion | The Method}

Decided in /jdi-new (D-1). Do not change.

## Slug
{project_slug}     # used in commits, branches, specialist names

## Research notes (optional)
- {fact 1}
- {fact 2}

## Global constraints
- Minimum coverage 80%
- Conventional Commits
- Atomic commits per task
- Language: code in English, discussion in English

## Definition of Done

**LOCKED — project-wide baseline.** Inherited by every phase's reviewer (Gate 8).

### Auto-verifiable
- [ ] `{test_command}` exits 0
      **Verify:** {executable check}
      **Source:** PROJECT

### Manual
- [ ] CHANGELOG.md updated with entry per release
      **Verify:** human confirmation required
      **Evidence:** new `## [version]` heading in CHANGELOG.md
      **Source:** PROJECT
```

**Who edits:** `/jdi-new` creates it (including `## Definition of Done`). Later: manual edit backed by a D-XX in DECISIONS.md (changing the baseline = locked decision). Agents never touch it.

**Size:** max 80 lines (100 for adopted brownfield projects — extra `## Existing assets` section). Concise. Cap 8 items in DoD.

## ROADMAP.md

```markdown
# {project_name} — Roadmap

## Phases

### Phase 1: {name}
- **Slug:** {slug}
- **Goal:** 1 line
```

No stored `total_phases` (0.11.0+): the phase count is DERIVED from the
`### Phase ` heading count — a stored counter conflicts on every parallel
add and union-merges to a stale number. Legacy ROADMAPs keep their line
(updated best-effort by add/remove-phase); readers always count headings.

No per-phase `Status:` lines and no current-phase pointer — phase status is derived from artifacts (see above), which keeps ROADMAP.md append/insert-only and conflict-free across parallel branches. The numeric `### Phase N` heading is display-only; the slug is the canonical ID (no `NN-` prefix in v2).

**Who edits:** `/jdi-new` (or `/jdi-adopt`) creates. `/jdi-add-phase` appends, `/jdi-remove-phase` removes a pending phase. `/jdi-discuss` may edit to clarify a goal (rare). `/jdi-ship` does NOT touch it — except on legacy pre-0.2.0 roadmaps that still carry `- **Status:**` lines, where ship updates that phase's line best-effort (it never adds such a line where none exists).

## STATE.md

```markdown
# {project_name} — State

project_slug: {slug}
schema_version: 2
specialists_ready: true | false
current_phase: 1                   # display mirror (legacy v1 readers)
current_phase_slug: setup-api      # v2 canonical phase ID
phase_status: ready | planned | executed | partial | verified | pending_manual_dod | blocked | paused | complete
phase_verdict: APPROVED | APPROVED_WITH_WARNINGS | APPROVED_PENDING_MANUAL | BLOCKED  (after verify)
next_step: /jdi-discuss setup-api
```

**STATE.md is ADVISORY and UNTRACKED (0.3.0+).** It is a next-step hint for this clone — gates never depend on it; they check phase artifacts (SHIPPED.md, REVIEW.md, ...). `current_phase_slug` is the canonical phase pointer in v2; `current_phase` stays as an integer display mirror (numeric parsers depend on it — completion is flagged separately via `all_phases_complete: true`, never by writing `done` into `current_phase`).

Since 0.3.0 it lives in `.gitignore` — every command rewrites it, so versioning it made it the last guaranteed merge conflict between parallel developers. Commands regenerate it from artifacts when absent (fresh clone); legacy projects that still track it keep working (commands stage it tolerantly: `git add .jdi/STATE.md 2>/dev/null || true`).

**Who edits:** every command updates it after running.

**Lifespan:** overwritten on each command. Never committed on 0.3.0+ projects. No history needed — it is derivable.

**`/jdi-loop`-specific statuses:**
- `paused` — user chose "adjust plan" at the human gate; edit PLAN.md/CONTEXT.md and re-run /jdi-loop
- `blocked` — `/jdi-verify` returned BLOCKED OR `/jdi-loop` was escalated/killed (human review required)

## config.json

```json
{
  "$schema_version": "1.2",
  "context_window": 200000,
  "thresholds": {
    "warn_pct": 60,
    "critical_pct": 70
  },
  "budgets": {
    "max_context_chars": 6000,
    "max_plan_chars": 12000,
    "max_summary_chars": 8192
  },
  "compaction": {
    "archive_after": 5
  },
  "orchestration": {
    "mode": "standard",
    "source": "default"
  },
  "coverage_min": 80
}
```

**Who edits:** `/jdi-new` writes it directly via Write if absent (default inlined in the command prompt). `templates-jdi-folder/config.json` is the canonical reference for the default, shipped by the npm package. User edits manually afterwards. Commands only read.

**Fields:**
- `context_window` — window of the model in use. 200k = default (Claude Sonnet/Opus). 1_000_000 for 1M-window models.
- `thresholds.warn_pct` — when the orchestrator warns "context heating up". Default 60%.
- `thresholds.critical_pct` — when the orchestrator suggests starting the next phase in a fresh session. Default 70% (fracture zone, based on context-rot research).
- `budgets.max_*_chars` — caps used by commands when truncating artifacts before inlining. Heuristic: ~4 chars/token.
- `compaction.archive_after` — phases older than this delta from the current position move to `.jdi/archive/` (executed by `/jdi-ship`).
- `coverage_min` — overridable per PROJECT.md. Reviewer uses it.
- `orchestration.mode` — `standard` (default) or `enhanced`. Host-neutral flag: when `enhanced` AND the host can orchestrate sub-agents, commands MAY run optional multi-agent layers (advisory critics); otherwise they degrade to the standard path. Off-path is byte-identical. Capability boolean, NOT a token ledger.
- `orchestration.next_execution` — `step` (default) or `loop`. With `loop`, `/jdi-next` routes the execute/verify states (`planned`, `executed`, `verified+BLOCKED`) to `/jdi-loop` instead of single `do`/`verify` steps. Per-project opt-in — ralph presumes a trustworthy test suite. Absent = `step`.
- `orchestration.source` — `default` | `user` | `detected`. Provenance/audit only, never drives behavior.

**Lifespan:** life of the project. Versioned in git.

**Read by:** `/jdi-do`, `/jdi-plan`, `/jdi-verify`, `/jdi-ship` (for compaction). Specialists (doer/reviewer) read `coverage_min`. `orchestration.mode` is read by `/jdi-verify` (and future consumers) at the top-level turn; sub-agents only see it through this file, never through the host session.

**Written by:** `/jdi-new` and `/jdi-adopt` (Step 4b — orchestration opt-in, default determined at the top-level turn where the host capability signal is visible).

## DECISIONS.md

```markdown
# {project_name} — Locked decisions

D-1 (2026-05-09): Code design = Vertical Slice. Rationale: ...
D-2026-05-09-setup-api-1 (2026-05-09, phase setup-api): Tests project setup already in phase 1. Reason: ...
D-2026-05-10-todo-crud-1 (2026-05-10, phase todo-crud): Validation via FluentValidation. Reason: ...
```

**Who edits:** APPEND-ONLY. `/jdi-new` creates it with D-1. `/jdi-discuss` appends D-XX per phase.

**Rules:**
- A locked decision never reverses — immutable
- Each entry has date + phase (if applicable) + 1-line rationale
- **v1 format (legacy):** sequential ID (`D-1`, `D-2`, ...). Racy in multi-dev — two branches allocate the same number.
- **v2 format (multi-dev safe):** deterministic ID `D-{YYYY-MM-DD}-{phase_slug}-{seq}` (e.g. `D-2026-05-09-setup-api-1`). No cross-branch collision.
- Migrated projects accept both formats on read; new writes follow `schema_version`.

## `phases/<slug>/SHIPPED.md` (v2; v1 legacy: `phases/NN-slug/`)

```markdown
shipped_at: 2026-05-10T14:22:31Z
verdict: APPROVED
by: {git user.name}

## Learnings
- Watch N+1 on repository queries — flagged twice by reviewer
- {max 5 one-line bullets; section omitted when nothing qualifies}
```

**Who edits:** `/jdi-ship` creates it (including the optional `## Learnings` — distilled from REVIEW.md warnings/blockers/waivers + SUMMARY.md blocked tasks). Nobody else touches it.

**Semantics:**
- This is the per-phase **done marker** — its existence means the phase is shipped (derived status `done`).
- Idempotency guard: `/jdi-ship` refuses to double-ship when the file already exists.
- Team-safe by design: completion is recorded IN THE PHASE FOLDER, not in ROADMAP.md — two developers shipping different phases on different branches produce zero merge conflicts.
- `## Learnings` is the cross-phase feedback channel: `/jdi-plan` (planner) and the doer read the SHIPPED.md of the up-to-3 most recently shipped phases and convert recurring items into acceptance criteria. Max 5 bullets, one line each — failure knowledge survives the phase without a central playbook file (which would be a merge hotspot and rot under rewrites).

## `phases/<slug>/LOOP.md` (optional, only with /jdi-loop; v1 legacy: `phases/NN-slug/`)

```markdown
---
phase: {N}
iter: 3
total_resets: 1
status: running | converged | escalated | paused | killed
max_iter_per_round: 5
max_resets: 3
created_at: 2026-05-10T10:30:00-03:00
---

## History (append-only)

- iter 1: BLOCKED, hash=abc123def4, commit=f8d2a1, ts=2026-05-10T10:31:00-03:00
- iter 2: BLOCKED, hash=abc123def4, commit=a91c33, ts=2026-05-10T10:33:00-03:00  <- oscillation!
- iter 3: BLOCKED, hash=de45ef9012, commit=2b3d77, ts=2026-05-10T10:36:00-03:00
- iter 4: BLOCKED, hash=de45ef9012, commit=8e1c44, ts=2026-05-10T10:38:00-03:00
- iter 5: BLOCKED, hash=11aa22bb33, commit=4f9e21, ts=2026-05-10T10:40:00-03:00
--- RESET 1 at 2026-05-10T10:42:00-03:00 ---
- iter 1: APPROVED_WITH_WARNINGS, hash=00ff11ee22, commit=c1d2e3, ts=2026-05-10T10:45:00-03:00
```

**Who edits:** `/jdi-loop` creates/appends. Nobody else touches it.

**Rules:**
- Frontmatter `iter` + `total_resets` + `status` are MUTABLE (overwritten)
- `## History` block is APPEND-ONLY (full audit trail, precise oscillation detection)
- `hash` = truncated SHA256 of normalized blockers/warnings — to compare iter N vs N-1
- `status: converged` => phase may proceed to `/jdi-ship`
- `status: killed` => hard cap reached (max_iter × max_resets), requires human review of PLAN/CONTEXT
- `status: escalated|paused` => user intervened; re-running `/jdi-loop <slug>` resumes
- `total_resets` is never reset. Resuming from `escalated|paused` CONSUMES a reset; crash-resume of `status: running` does not.
- The only way past `killed` is the explicit `--reset-loop` flag (confirmed by the user, audited — the old file is archived as `LOOP.md.killed-{ts}`).

**State transitions:**
```
running → converged   (verdict APPROVED or APPROVED_WITH_WARNINGS)
running → escalated   (user chose abort at the human gate)
running → paused      (user chose to adjust the plan at the human gate)
running → killed      (total_resets >= max_resets)
escalated|paused → running (re-running /jdi-loop resumes — consumes a reset)
killed → fresh LOOP.md     (only via --reset-loop, explicit human decision)
```

## Memory levels

| Level | File | Lifespan |
|---|---|---|
| Project | `PROJECT.md` | Life of the project (immutable after /jdi-new) |
| Roadmap | `ROADMAP.md` | Life of the project (append/insert-only; no status lines) |
| Config | `config.json` | Life of the project, manually editable |
| Decision | `DECISIONS.md` | Append-only, never deleted |
| Routing | `specialists.md`, `reviewers.md` | Append-only |
| Skills | `skills-registry.md` | Append-only |
| Audit | `registry.md` | Append-only |

**No generic MEMORY.md file (v1 had one).** It was a catch-all that got messy. Replaced by:
- DECISIONS.md (formal decisions)
- registry.md (agent/specialist creations)
- SUMMARY.md per phase (execution learning)
- REVIEW.md per phase (warns/blockers as learning)

## Read-depth per level (token budget)

Hard rule — reference in `ARCHITECTURE.md > Read-depth scaling`. Summary here for those who only read MEMORY.md:

| Distance from current phase | Allowed read |
|---|---|
| Current phase | Full body |
| Previous phase | Frontmatter + REVIEW verdict only |
| 2+ phases back | Do not read body. List/`head` only |
| `.jdi/archive/` | Treat as a distant phase. Do not read body |

PROJECT.md, ROADMAP.md, DECISIONS.md, config.json: full read **always allowed** — they are short by design and stable (good prompt-cache prefix candidates).

Exceptions:
- `jdi-asker` reads up to 2 previous CONTEXT.md files (agent rule)
- `/jdi-verify` reads the previous phase's PLAN.md if a current task references a `D-XX` from that phase (traceability)
- `jdi-planner` and the doer read `## Learnings` from SHIPPED.md of the up-to-3 most recently shipped phases (≤10 lines each — cross-phase feedback, cheap by design)
