# JDI — Architecture

## Principles

1. **Fresh context per agent** — each spawn gets a clean window. Anti context-rot
2. **Thin orchestrator** — the command loads context, spawns the agent, routes. Nothing else
3. **File-based state** — `.jdi/` in md/json. No DB, no server
4. **Locked decision = immutable** — D-XX never reverses
5. **1 task = 1 atomic commit**
6. **The plan is the prompt** — PLAN.md is already the executor's input
7. **Per-project specialists** — doer/reviewer customized per project, not generic
8. **Wave-based parallelism** — parallel within a wave, sequential between waves
9. **Security > Perf > Best Practices** — fixed order on conflict

## Layered structure

```
core/                    <- shipped, generators (lives in the JDI repo)
  agents/                <- 7 core agents
    jdi-researcher.md    <- greenfield discovery (/jdi-new)
    jdi-adopter.md       <- brownfield discovery (/jdi-adopt)
    jdi-bootstrap.md
    jdi-asker.md
    jdi-planner.md
    jdi-architect.md
  commands/              <- 17 commands
    jdi-new.md, jdi-adopt.md, jdi-bootstrap.md, jdi-discuss.md,
    jdi-plan.md, jdi-do.md, jdi-verify.md, jdi-confirm-dod.md,
    jdi-ship.md, jdi-loop.md, jdi-status.md, jdi-add-phase.md,
    jdi-remove-phase.md, jdi-migrate-phases.md, jdi-create.md
  skills/                <- 13 core skills
    dry, kiss, yagni, solid, clean-code            (principles — always loaded)
    ddd, clean-architecture, hexagonal, onion,
    vertical-slice, the-method                     (code-design — exactly ONE per project)
    frontend-rules, frontend-validator             (conditional on has_frontend)
  templates/             <- 5 templates
    agent.md, skill.md
    dod-schema.md            <- canonical Definition of Done item format
    doer-specialist.md       <- used by the architect in specialist mode
    reviewer-specialist.md   <- idem

.jdi/                    <- per-project state (generated by /jdi-new or /jdi-adopt)
  PROJECT.md, ROADMAP.md, DECISIONS.md, STATE.md (schema_version: 2)
  config.json            <- token budgets, models per role, thresholds, compaction, loop, orchestration mode
  stacks/<name>.json     <- gate commands per reviewer, run by `jdi-cli gates run` (0.17+)
  known-errors/<ID>.md   <- one known error per file, with stage + globs (0.17+)
  cache/                 <- untracked: briefs/, gates/, learnings, decisions index
  todos.md               <- scope creep captured by the asker (optional)
  specialists.md, reviewers.md, registry.md
  agents/                <- per-project specialists (generated by /jdi-bootstrap)
    jdi-doer-{slug}.md
    jdi-reviewer-{slug}.md
  phases/<slug>/         <- v2 layout (default for new projects)
    CONTEXT.md, PLAN.md, SUMMARY.md, REVIEW.md
    SHIPPED.md           <- completion marker written by /jdi-ship
    LOOP.md              <- only if /jdi-loop ran (written by `jdi-cli loop`)
    verify/dod-N.sh      <- long DoD `Verify:` bodies (`jdi-cli dod extract`)
  phases/NN-<slug>/      <- v1 legacy layout (never renamed post-migration)
  archive/               <- old phases moved by ship compaction + removed-<slug>/ folders

bin/lib/                 <- shared helpers (shipped via npm files whitelist)
  jdi-resolve-phase.{sh,ps1}    <- int OR slug → {slug, dir, position, schema, exists}
  jdi-validate-slug.{sh,ps1}    <- shape + reserved + --check-unique
  jdi-monitor.{sh,ps1}          <- context budget warm-up
  jdi-truncate.{sh,ps1}         <- max_chars enforce
  jdi-core.js                   <- config, phases (resolve-phase is Node since 0.17), frontmatter
  brief.js, gates.js, dod.js, review.js, loop.js, next.js, phase-ops.js,
  budgets.js, known-errors.js, specialists.js, cost.js, ...   <- token-economy helpers (Node, zero deps)
```

The `bin/lib` helpers are exposed as **CLI subcommands** — slash commands call them via `npx -y jdi-cli resolve-phase|validate-slug|truncate|monitor` (`resolve-phase --json` for PowerShell consumers). No helper code is ever copied into the consumer repo (no-code-in-consumer-repo invariant); the same rule makes git hooks **opt-in** at install (`--githooks`).

**Build pipeline:** `core/` is the single source of truth; `bin/jdi-build.{sh,ps1}` generates `runtimes/` (one adapter per runtime). Both builders emit byte-identical output (UTF-8 without BOM, LF), and the repo's `.gitattributes` pins line endings so cross-shell builds produce zero ghost diffs. Never edit `runtimes/` by hand.

## Lifecycle

```
/jdi-new "<description>"          -> PROJECT.md (+ § DoD baseline) + ROADMAP.md + STATE.md (schema v2) + DECISIONS.md + config.json
/jdi-adopt ["<description>"]      -> same outputs for existing code (adopted: true, D-2 boundary commit, § Existing assets)
/jdi-bootstrap                    -> .jdi/agents/jdi-doer-{slug} + jdi-reviewer-{slug} (multi-stack: N pairs)
                                     + runtime copies via `jdi-cli sync-specialists` (.claude/agents/ etc. — what the runtime spawns from)
/jdi-discuss <slug|position>      -> phases/<slug>/CONTEXT.md (+ § DoD phase-specific)
/jdi-plan    <slug|position>      -> phases/<slug>/PLAN.md (tasks + waves)
/jdi-do      <slug|position>      -> atomic commits + phases/<slug>/SUMMARY.md
/jdi-verify  <slug|position>      -> phases/<slug>/REVIEW.md (gates 1-8 + DoD Checklist; recreated per run)
/jdi-confirm-dod <slug|position>  -> REVIEW.md DoD rows flipped (CONFIRMED/REJECTED) + verdict recomputed
/jdi-ship    <slug|position>      -> phases/<slug>/SHIPPED.md + STATE advance + archive compaction + tag (optional)

/jdi-loop    <slug|position>      -> ralph mode: do <-> verify bounded auto-loop (LOOP.md)
/jdi-status                       -> read-only snapshot (status derived from artifacts)
/jdi-add-phase / /jdi-remove-phase-> roadmap mutation (slug-as-ID, multi-dev safe)
/jdi-migrate-phases               -> v1 → v2 stamp in STATE.md (non-destructive)
```

Dual phase ID: slug (canonical) or int position (display/legacy). The resolver (`npx -y jdi-cli resolve-phase`) normalizes to `{slug, dir, position, schema_version, folder_exists}`. v1 → v2 via `/jdi-migrate-phases` (non-destructive).

Gates between steps:

| From | To | Gate |
|---|---|---|
| /jdi-new (or /jdi-adopt) | /jdi-bootstrap | PROJECT.md + ROADMAP.md exist (PROJECT § DoD present) |
| /jdi-bootstrap | /jdi-discuss | `.jdi/agents/jdi-doer-*` + `jdi-reviewer-*` exist (**enforced** — discuss aborts without them) |
| /jdi-discuss | /jdi-plan | CONTEXT.md exists + clear locked decisions + CONTEXT § DoD present |
| /jdi-plan | /jdi-do | PLAN.md valid (tasks + acceptance + files_modified) |
| /jdi-do | /jdi-verify | SUMMARY.md exists (all tasks completed or marked blocked) |
| /jdi-verify | /jdi-confirm-dod | REVIEW.md verdict == APPROVED_PENDING_MANUAL (manual DoD pending) |
| /jdi-confirm-dod | /jdi-ship | no DoD Checklist row still MANUAL_REQUIRED (REJECTED rows = audited waivers, do not block) |
| /jdi-verify | /jdi-ship | REVIEW.md verdict ∈ {APPROVED, APPROVED_WITH_WARNINGS} + zero MANUAL_REQUIRED + SHIPPED.md absent |

Reviewer is **read-only** by design. It only runs gates, never fixes.

## Core agents x per-project specialists

**Core (shipped, in `core/agents/`):**
- `jdi-researcher` — greenfield discovery, generates PROJECT.md + ROADMAP.md
- `jdi-adopter` — brownfield discovery: scans manifests/layout/git/docs, infers stack + code-design, ALWAYS confirms code-design with the user, records the D-2 boundary commit (coverage enforced only on files created after adoption)
- `jdi-bootstrap` — wrapper that triggers the architect in specialist mode (+ the mandatory multi-stack question)
- `jdi-asker` — adaptive question loop (CONTEXT.md)
- `jdi-planner` — decomposes the phase into tasks + waves
- `jdi-architect` — meta. 2 modes: `create` (agents/skills in core/) or `specialist` (per-project doer/reviewer)

**Per-project (generated, in `.jdi/agents/` — source of truth; the runtime reads the generated copy in its own agent dir, kept in sync by `jdi-cli sync-specialists` through the same frontmatter emitter as `build`):**
- `jdi-doer-{slug}` — executor that ALREADY KNOWS stack/conventions/code-design. No discovery
- `jdi-reviewer-{slug}` — gates customized to the stack (build/test/coverage/lint/security)

Specialist routing via `.jdi/specialists.md` and `.jdi/reviewers.md` (multi-stack: one row per pair with a `File glob` column).

## Wave-based parallelism

`/jdi-do <phase>`:
1. Reads PLAN.md, groups tasks into waves (wave M = tasks that only depend on wave M-1)
2. For each wave:
   - Intra-wave overlap check (files_modified disjoint?)
   - If 2+ parallel tasks AND no overlap AND not `--sequential`:
     - Sequential dispatch — ONE `Agent()` per message with `run_in_background: true`
     - Waits for the whole wave before the next
   - Otherwise: runs sequentially, 1 doer per task
3. After all waves: doer writes the final SUMMARY.md

Sequential dispatch avoids the `.git/config.lock` race (a well-documented git worktree problem).

## Question loop (jdi-asker)

Adaptive. Rules:

1. Reads PROJECT.md, ROADMAP.md, DECISIONS.md
2. Reads up to 2 previous CONTEXT.md files (max)
3. Identifies 3-5 phase-specific gray areas (not generic categories)
4. Asks one at a time via AskUserQuestion
5. Each answer becomes a locked decision in DECISIONS.md — schema v2 IDs are `D-{YYYY-MM-DD}-{phase_slug}-{seq}` (collision-free across branches); v1 keeps `D-N` increments
6. Stops when the user says "enough" / "go" / 5 questions reached
7. Writes CONTEXT.md with decisions + canonical_refs

## Execution loop (jdi-doer-{slug})

Per task in PLAN.md:

1. Reads the task (files_modified, acceptance, dependencies, test)
2. Implements the code
3. Runs the test command (`{TEST_COMMAND}` defined in the specialist)
4. On failure -> adjusts and retries. **Max 3 attempts.** After the 3rd, marks the task `blocked` and continues
5. Atomic commit: `feat({phase-slug}): {task summary}` (Conventional Commits)
6. Appends a line to SUMMARY.md
7. Next task

## Post-execution review (jdi-reviewer-{slug})

`/jdi-verify <phase>` dispatches the reviewer. REVIEW.md is deleted and recreated on every run (stale verdicts can never poison the aggregation; git history keeps prior runs). 8 gates:
1. Build
2. Tests
3. Coverage (>= PROJECT.md threshold, default 80%)
4. Lint/Format
5. Security/Perf rules for the stack
6. Plan consistency (commits match files_modified)
7. UI Validation (conditional — only if `frontend.has_frontend: true`)
8. Definition of Done — parses `PROJECT.md § DoD` + `CONTEXT.md § DoD`, runs `Verify:` per item, classifies Auto PASS/FAIL and Manual MANUAL_REQUIRED

Verdict:
- APPROVED — all gates PASS, no manual DoD pending
- APPROVED_WITH_WARNINGS — no blockers, some warns
- **APPROVED_PENDING_MANUAL** — gates 1-7 OK, DoD auto PASS, but Manual items awaiting human confirmation via `/jdi-confirm-dod`
- BLOCKED — gate 1-3 failed OR gate 5 critical OR gate 8 Auto FAIL OR gate 7 BLOCK

The consuming commands (verify/ship/loop/confirm-dod) read the **aggregate verdict as worst-case across ALL verdict lines** (multi-stack writes one per reviewer segment): BLOCKED > APPROVED_PENDING_MANUAL > APPROVED_WITH_WARNINGS > APPROVED. Legacy pt-BR `Veredicto:` lines are accepted; an empty/missing verdict is treated as a malformed review and aborts (never ship on silence).

BLOCKED blocks `/jdi-ship`. APPROVED_PENDING_MANUAL also blocks `/jdi-ship` — it requires `/jdi-confirm-dod` first.

Optional: when `config.json` has `orchestration.mode: "enhanced"` and the host can spawn read-only sub-agents, `/jdi-verify` adds a **DoD critic** pass that re-examines Auto-PASS DoD rows for hollow gates (exit 0 without proving the criterion). It can only tighten the verdict, never loosen it; the standard path is byte-identical when unavailable.

## Definition of Done (DoD)

DoD is captured in two layers and verified at Gate 8:

| Layer | Where | When | Who | Cap |
|---|---|---|---|---|
| Project-wide | `PROJECT.md § Definition of Done` (LOCKED) | `/jdi-new` Stage 2 | jdi-researcher | 8 items |
| Phase-specific | `phases/<slug>/CONTEXT.md § Definition of Done` (LOCKED) | `/jdi-discuss` Stage 2 | jdi-asker | 10 items |
| Task acceptance | `PLAN.md` per task | `/jdi-plan` | jdi-planner | 8 tasks/phase |

Every DoD item has a mandatory `Verify:` (a command OR "human confirmation required"). Vague items are rejected at capture. Canonical format in `core/templates/dod-schema.md`.

Flow:
- Capture → `/jdi-new` (PROJECT) + `/jdi-discuss` (CONTEXT)
- Verification → the reviewer's Gate 8 runs Auto items; collects Manual items as MANUAL_REQUIRED in the `## DoD Checklist` table (single source of truth)
- Manual confirmation → `/jdi-confirm-dod` walks each MANUAL_REQUIRED row and flips its Status cell: `CONFIRMED` (with mandatory evidence) or `REJECTED` (audited waiver with mandatory justification — does NOT block ship)
- Ship → `/jdi-ship` requires aggregate verdict ∉ {BLOCKED, APPROVED_PENDING_MANUAL} AND zero rows still MANUAL_REQUIRED in the DoD Checklist

## Team model

Multi-developer coordination rests on five invariants:

1. **Status is derived from artifacts, never stored.** The ladder: `SHIPPED.md` → done, `REVIEW.md` → verified, `SUMMARY.md` → executed, `PLAN.md` → planned, `CONTEXT.md` → discussed, nothing → pending. Any clone computes the same answer from the files alone.
2. **STATE.md is advisory and untracked (0.3.0+).** It is a per-clone next-step cache in `.gitignore`; no gate depends on it and it never reaches a merge. Commands regenerate it from artifacts when absent (fresh clone): current phase = first ROADMAP phase without `SHIPPED.md`.
3. **IDs are collision-free.** Phases are identified by slug (validated shape + reserved words + uniqueness); decisions on v2 use `D-{YYYY-MM-DD}-{slug}-{seq}`; registry entries use `R-{YYYY-MM-DD}-{slug}`. Two devs on parallel branches never silently collide — same-slug races surface as explicit git conflicts.
4. **The roadmap is one file per phase (layout v3, 0.13.0+).** `.jdi/roadmap/{slug}.md` with an `order:` frontmatter (fractional on insert-between — no sibling is ever renumbered) is the source of truth; `.jdi/ROADMAP.md` is an untracked view rendered in the legacy format so every reader keeps its path. It carries no per-phase status and no current-phase pointer; `/jdi-ship` never touches it. Developers adding or shipping different phases touch disjoint files — nothing to merge.
5. **Multi-writer streams are per-entry files, not shared appends.** Server-side PR merges (GitHub/GitLab/ADO) IGNORE `.gitattributes` merge drivers, so the old `merge=union` protection never applied where teams actually merge — the PR page (proven by a live PR conflicting on DECISIONS.md/ROADMAP.md/todos.md despite union; Kubernetes dropped union for the same reason). v3 removes the conflict class structurally: decisions → `.jdi/decisions/D-{date}-{slug}-{seq}.md` (filename = ID), todos → `.jdi/todos/{date}-{slug}.md`, bootstrap//jdi-create output → `.jdi/registry/R-{date}-{slug}.md` (fenced sections feed the `registry.md`/`specialists.md`/`reviewers.md`/`skills-registry.md` views). Views are untracked and regenerated by `npx -y jdi-cli render` (byte-deterministic across `.sh`/`.ps1`); a pre-commit gate and the CI artifacts gate turn any committed view/LEGACY file red. Legacy projects migrate with the idempotent `npx -y jdi-cli migrate-layout` (splits the roadmap, freezes the old files as `LEGACY*` via `git mv`, unions removed — not needed). Not applied to PROJECT.md/config.json — conflicts there must stay visible, as must remove-vs-edit races (modify/delete on a phase's files).

## Read-depth scaling (token budget)

Hard rule: **each agent reads only what its step needs, and every read is paid
again on each later turn of that agent.** Files read by one agent are NOT a
cache prefix for the next one (measured: a fresh spawn shares ~2-3k cached
tokens with earlier ones; the rest is written to the cache again), so "long-term
files are short and cached" is not a reason to read them whole.

Since 0.17 every agent starts from a **brief** — `jdi-cli brief <phase> --role
<r>` writes one capped file to `.jdi/cache/briefs/<slug>/` (sections shortened
with a pointer before any is dropped; the cap is `budgets.brief_tokens`) and the
dispatch passes only its path:

| Who | Brief carries | Opens on demand | Never reads |
|---|---|---|---|
| doer (`--task T-N`) | its task block, orchestrator notes, the decisions the task cites, the DoD lines for its files, known errors for its files and stage, `learnings --last 3`; in fix mode `review blockers` | the files of its task, `decisions --ids` | other tasks, other phases, whole DECISIONS.md / CONTEXT.md |
| reviewer (`--stack s`) | its scope and changed files, the gate results already measured (`gates run`), the task list, the DoD rows of its stack, decisions for Gate 6, known errors | the diff of its glob, a gate log | other phases, previous REVIEW copies |
| asker | PROJECT § vision/stack/design/constraints, the roadmap entry, decisions of the init + 2 most recent phases (one line each), known errors for the DoD | `.jdi/cache/dod-schema.md` | old CONTEXT.md bodies, whole DECISIONS.md |
| planner | goal, locked decisions, DoD (Verify by reference), stack and code design, routing table, learnings, known errors | code ranges | specialist bodies, old PLAN.md files |
| everyone | — | — | instruction files the runtime injects (CLAUDE.md, AGENTS.md, rules) |

**Deterministic steps live in the CLI, not in the prose.** Anything the
orchestrator used to compute turn by turn — the next command and the status
screen (`next`), the roadmap entry (`add-phase`), the verdict (`review
verdict`), the ralph loop's history and decisions (`loop record/reset`), the
gates (`gates run`, outside any agent's context), the DoD lint/extraction
(`dod`), shipping (`ship`) — is one call with a short answer.

**How to apply (orchestrator):**
- Dispatch prompts carry ids (`phase_slug`, `task`, `mode`), never content.
- Agents return at most 10 lines; read verdicts and counts with grep.
- New work = new agent. Parallel cards = one session per worktree. One phase =
  one orchestration session.
- Budgets per artifact live in `.jdi/config.json` `budgets` (tokens, with
  `chars_per_token` per language), checked by `validate-phase --budgets` and
  enforced for phases created with 0.17+ (`created_with` in the roadmap
  entry). Long `Verify:` bodies go to `{phase_dir}/verify/dod-N.sh`
  (`jdi-cli dod extract`), so CONTEXT.md stays small for every reader.
- Long suites never run inside a large agent context: `/jdi-verify` runs them
  through `gates run` (`.jdi/stacks/<name>.json`) and the reviewers read the
  JSON — a sub-agent's prompt cache lives 5 minutes, and a long command inside
  it makes the next call re-write the whole context.
- `npx jdi-cli cost --targets` measures all of this from the local Claude Code
  transcripts.

## Hooks

Git hooks are **opt-in**: `jdi install --githooks` copies no-op `pre-commit` and `post-commit` scripts to `.githooks/`. The default install copies NO shell scripts into the consumer repo (no-code-in-consumer-repo invariant). Doer/reviewer cover docs/quality responsibilities inside the normal flow.

Users can customize `.githooks/` for:
- Fast pre-commit lint
- Post-commit Slack notification
- Etc.

## Not 100% spec-driven

JDI is not pure Spec-Driven Development. Orthodox spec requires spec before code, traceability down to tests, stakeholder sign-off.

JDI does:
- CONTEXT.md = spec lite. Locked decisions, nothing more
- PLAN.md = task list with acceptance. Traceability via D-XX
- No stakeholders. Just the user

When the user needs a formal spec -> use a dedicated governance tool. JDI is a dev workflow, not governance.
